Saved threads (bookmarks)

Logged-in users can save any thread with one click, from the feed or from the thread page, and find all their saved threads in a new Saved tab on their Profile.

Spec §1 · Problem / motivation

Why bookmarks

ThreadHive has no way to keep a thread for later. The feed is newest-first with five threads per page, so a thread a user meant to come back to drifts out of reach within a few visits. Today the only workaround is remembering the title or the URL.

Bookmarks give users a private, persistent list of threads they care about, and that list is a concrete reason to return to the app.

It builds on what already exists: thread cards in the feed (ThreadList.jsx), the single-thread view (ThreadCard.jsx), the Profile page (/profile), and JWT login on every API route (authHandler), which identifies the user on each request.

Decided while drafting

  • The Save toggle appears on feed cards and on the thread page.
  • Saved threads appear in a Saved tab on Profile, which can be linked as /profile?tab=saved.
  • Change from the epic draft: no separate /saved page and no Sidebar link. This also keeps the feature out of Sidebar.jsx, which another epic feature edits.
Spec §2

User stories

  1. As a logged-in user, I can save a thread from the feed with one click, without opening it.
  2. As a logged-in user, I can save or unsave a thread from its thread page.
  3. As a logged-in user, I can see at a glance whether a thread is already saved, wherever its card appears.
  4. As a logged-in user, I can open the Saved tab on my Profile and see the threads I saved, newest first, with when I saved each one.
  5. As a logged-in user, I can unsave a thread directly from the Saved tab.
  6. As a logged-in user, my saved threads are private: no other user can see or change them.
  7. As a logged-in user, I can share or bookmark a link to my Saved tab (/profile?tab=saved).

Behaviour

What happens when a user clicks Save

The button updates first and the server confirms afterwards. If the server rejects the save, the change is undone. Saves can safely be repeated (the API is idempotent), so retries and double-clicks can never leave the toggle in the wrong state.

Spec §5

Data model

FieldTypeRules
userObjectId → "User"Required. Always taken from the login token (req.user.userId), never from the request body.
threadObjectId → "Thread"Required. The saved thread.
createdAtDateAutomatic, from { timestamps: true }. Sent to clients as savedAt.
updatedAtDateAutomatic. Unused.

Why a separate collection

  • Leaves User.js untouched. A savedThreads array on the user would grow without limit.
  • Records when each thread was saved, so the list can sort newest-saved first and show "saved 2h ago".
  • The unique compound index prevents duplicates at the database level.
  • No migration: MongoDB creates the collection on the first save.
Spec §4

API contract

Applies to all four endpoints

  • Auth: Authorization: Bearer <jwt>, enforced by authHandler. Without a valid token: 401 "No token provided, authorization denied." or "Token is not valid."
  • Envelope: { success, message, data }. Errors are raised with createAppError and returned as { success: false, message }.
  • Routing: new router src/routes/bookmarks.js, mounted at /api/bookmarks. /ids is declared before /:threadId.
  • Why PUT / DELETE instead of one toggle endpoint: the client always knows the state it wants. With repeat-safe calls, retries and double-clicks can't flip the state the wrong way.
GET/api/bookmarksLists the caller's saved threads for the Saved tab.
StatusMessagedata
200"Bookmarks fetched successfully"An array of saved thread objects (below), newest savedAt first. [] if there are none.
401Missing or invalid token
Bookmarks whose thread has been deleted are left out of the response and deleted in the same request.
GET/api/bookmarks/idsIds of every thread the caller has saved. Loaded once per session so cards can show their saved state.
StatusMessagedata
200"Bookmark ids fetched successfully"string[] of thread ids, unordered. Excludes threads that no longer exist.
401Missing or invalid token
Having a separate ids endpoint means thread payloads elsewhere in the app don't need an isSaved field, which keeps this feature out of threadService.js.
PUT/api/bookmarks/:threadIdSaves a thread. Safe to repeat. No request body.
StatusMessagedata
200"Thread saved"{ threadId, saved: true, savedAt }. Repeat calls return the original savedAt.
400"Invalid thread id"threadId is not a valid ObjectId
404"Thread not found"No thread with that id
401Missing or invalid token
If two saves arrive at once and one hits the unique index (MongoDB duplicate-key error 11000), that save is treated as successful and returns the existing bookmark.
DELETE/api/bookmarks/:threadIdUnsaves a thread. Safe to repeat.
StatusMessagedata
200"Thread unsaved"{ threadId, saved: false }. Also returned when nothing was saved.
400"Invalid thread id"threadId is not a valid ObjectId
401Missing or invalid token
The thread doesn't have to exist, so a user can remove a bookmark whose thread was deleted.

Spec §6

UI changes

BookmarkButton states

Not savedOutline icon bi-bookmark · aria-pressed="false" · label "Save thread"
SavedFilled icon bi-bookmark-fill · aria-pressed="true" · label "Unsave thread"
Request in flightDisabled wherever this thread appears until the server answers

A small link-style button using the app's existing color variables, so it works in light and dark themes. It takes one prop, threadId.

Redux: bookmarkSlice (registered as bookmarks)

State keyMeaning
savedIdsIds of saved threads. Drives every toggle and the tab count.
idsStatusidle · loading · succeeded · failed
savedThreadsSaved thread objects for the Saved tab
threadsStatusidle · loading · succeeded · failed
threadsErrorError message, or null
pendingIdsThreads with a save or unsave in flight

How the state changes

  • Thunks: fetchBookmarkIds, fetchSavedThreads, toggleBookmark({ threadId, save }). Failures go through handleApiError.
  • Toggle pending: add to pendingIds, then add to or remove from savedIds straight away. On unsave, also drop the thread from savedThreads.
  • Toggle succeeded: remove from pendingIds.
  • Toggle failed: remove from pendingIds and restore savedIds. The list refetches the next time the tab opens.
  • Vote sync: when threadSlice's upvote or downvote succeeds, update that thread's counts in savedThreads (same pattern as selectedThreadSlice).
  • Logout: reset everything on the "auth/logout" action type.

Profile page structure

  1. Header card looks the same: avatar, name, and the Edit / Save / Cancel buttons. The buttons show only while the Details tab is active.
  2. Tabs (details and saved), driven by the ?tab= query parameter. A missing or unknown value opens Details. The Saved tab is titled "Saved (N)", where N is the number of saved threads.
  3. Details tab holds the existing field grid and edit form, unchanged.
  4. Saved tab reloads the list and resets to page 1 every time it's opened. It shows a loading, error-with-Retry, empty, or list state; the list is 5 per page.

Spec §7

Edge cases & error handling

CaseExpected behaviour
Thread id isn't a valid ObjectId (e.g. abc)400 "Invalid thread id". Without this check, Mongoose would throw an error the app turns into a 500.
Saving a thread that doesn't exist or was just deleted404 "Thread not found". The toggle reverts.
Thread deleted after it was savedLeft out of both GET endpoints; the orphaned bookmark is deleted on the next GET /api/bookmarks. No toggle can appear for it, because the thread no longer renders anywhere.
Double-click or rapid togglingThe toggle is disabled while a request is pending (AC-5), and the server is repeat-safe either way.
Two saves at once, e.g. from two browser tabsThe unique index plus duplicate-key handling leave one document, and both requests return 200 (AC-22).
Unsaving something that isn't saved200; nothing changes.
Login expires mid-session401; the existing handleApiError clears the stored session and redirects to /login.
Loading saved ids fails at startupidsStatus: 'failed'; toggles show as not saved. Saving still works because PUT is repeat-safe. The ids load again when the Saved tab opens.
User saves from the feed while the Saved list is out of dateThe Saved tab reloads every time it's opened (AC-13).
Unsaving the only item on the last pageThe view moves back to the new last page (AC-16).
Unknown ?tab= valueOpens Details.
Logout, then login as another userBookmark state resets on auth/logout, and the ids load again for the new user (AC-25).
Bookmarks changed on another device or tabThis tab may be out of date until a reload or until the Saved tab is reopened. Accepted for v1.
A user with a very large number of bookmarksNo limit in v1. The server returns the whole list and the browser paginates it. See Out of scope.
Spec §8

Out of scope

  • A dedicated /saved page or a Sidebar "Saved" link. The epic draft proposed both; this spec puts the list on Profile only, as requested.
  • Bookmarking comments or subreddits.
  • Folders or collections, notes on bookmarks, and reordering, sorting or filtering the saved list.
  • Public or shared saved lists, and save counts shown on threads.
  • Server-side pagination of GET /api/bookmarks. Revisit if users routinely pass about 200 bookmarks.
  • Deleting bookmarks at the moment a thread is deleted. Cleanup on read covers it, and the alternative would mean editing threadService.js, which another epic feature also changes.
  • Pre-existing issues, tracked separately: GET /api/threads and GET /api/subreddits/:id send author password hashes to the browser, and anyone logged in can edit or delete any thread. This feature's endpoints must not leak (AC-23), but fixing the existing endpoints is a separate change.
  • Saving profile Details fields (bio, location, website) to the server.
Spec §9

Test plan

Backend unit BE unit

Vitest with mocked models, following the existing voteService.test.js.

  • bookmarkService.test.js:
    • Save creates a bookmark. A repeat save returns the original savedAt. Error 11000 counts as success. Invalid id gives 400 without a query; a missing thread gives 404.
    • Remove deletes the bookmark, does nothing when there is none, and gives 400 for an invalid id.
    • The list is newest-first, maps savedAt, drops and deletes orphans, and returns author and subreddit as { _id, name } only.
    • The ids list contains only threads that still exist.
  • bookmarkController.test.js: passes req.user.userId and threadId through, checks status, message and envelope, and lets service errors propagate.

Backend integration BE int

Supertest against an in-memory MongoDB, in tests/integration/bookmark.test.js. Two users register and log in. await Bookmark.init() runs first so the unique index exists, and Bookmark, Thread and Subreddit are cleared before each test without touching tests/setup.js.

  • All four endpoints return 401 without a token.
  • A save shows up in both GET endpoints, with the right savedAt and author/subreddit shapes.
  • Two sequential saves and two concurrent saves (Promise.all) each leave one document, return 200 and keep the same savedAt.
  • Unsave removes the thread. Unsaving something not saved returns 200.
  • A missing thread gives 404 and abc gives 400.
  • A deleted thread disappears from both GETs and its bookmark document is removed.
  • User B never sees user A's bookmarks.
  • Three saves come back newest-first.
  • No password or email key appears anywhere in a response.

Frontend unit FE unit

Vitest, jsdom, React Testing Library and MSW.

  • bookmarkSlice.test.js: immediate add and remove, revert on failure, the pending lifecycle, unsave dropping the thread from the list, vote sync, reset on auth/logout, and the fetch thunks.
  • BookmarkButton.test.jsx: icon, aria-pressed and label in both states; a click dispatches with the right save flag; disabled while pending.
  • formatRelativeTime.test.js: just now, minutes, hours, days, and more than 30 days.

Frontend integration FE int

Redux with MSW, following threadFlow.test.jsx, in tests/integration/bookmarkFlow.test.jsx.

  • Loading ids fills savedIds.
  • A save ends with the id saved and nothing pending; an unsave removes it from both savedIds and savedThreads.
  • When PUT returns 500 (via server.use), savedIds reverts.
  • The saved list arrives in the server's order.

Manual check before merge

  1. Run both apps (npm run dev in each).
  2. Save a thread from the feed, then open it: the toggle is filled.
  3. Reload the page: the thread is still saved.
  4. Open /profile?tab=saved: the thread is listed with "saved just now".
  5. Unsave it there: the row disappears and the count drops.
  6. Delete a saved thread through the API: it is gone from the Saved tab.
  7. Repeat in dark mode.
